# Introduction 💡

**R2ABENCH** is a dataset designed to evaluate models’ ability to generate system architecture designs from PRDs (Product Requirement Documents). It contains 17 data samples, each extracted from a high-quality software project, comprising 9 Python projects and 8 Java projects across diverse application domains.

## Repository Structure

- **/Dataset**  
  The complete dataset is stored in this directory.

- **/Outputs**  
  This folder contains the testing results generated by different models.

- **/Evaluation**  
  The code for the comprehensive evaluation framework used to assess the generated results is provided in this directory.

## Dataset Format

The dataset is organized by programming language, divided into Python and Java. Each project repository contains the reference architecture diagrams (`ad.wsd` and `ad.png`), the original architecture diagrams stored in the `ad` folder, as well as both Chinese and English versions of the PRD.

Each PRD consists of six sections, summarized as follows:

- **System Introduction**: Provides an overview of the system’s basic functionality, application background, technical framework, and target users, offering overall context for subsequent analysis.  
- **Core Objectives**: Summarizes the primary goals the system aims to achieve, focusing on high-level objectives without involving specific functionalities or implementation details.  
- **Functional Features**: Describes the core capabilities of the system through functional modules, using a “when–then” format to specify the behavior of entities under certain conditions.  
- **Technical Constraints**: Defines the technical requirements and limitations that must be followed during system implementation, such as development frameworks, communication protocols, and runtime environments.  
- **Non-functional Requirements**: Focuses on system performance and quality attributes, including response time, reliability, and security, ensuring service quality in real-world operation.  
- **System Architecture Description**: Provides a high-level overview of the system structure, dividing it into the application layer, support layer, and infrastructure layer, and explaining their organization and interactions.  

## Generate and Evaluation

To evaluate the generated results, run the `./run.sh` script in the `/Evaluation` directory. The script supports the following parameters:

- **setting**: Controls the structure of the input PRD for RQ analysis. Options include:  
  - `FULL`: includes all six sections  
  - `-Arch`: excludes the *System Architecture Description* section  
  - `MIN`: includes only *Core Objectives* and *Functional Features*  

- **generate_model**: The model used for generation.  
- **judge_model**: The model used for node alignment and scoring.  
- **dataset_dir**: The path to the dataset repository.  

### Example

```bash
python main.py \
    --setting "Arch" \
    --generate_model "gpt-5" \
    --judge_model "o3" \
    --dataset_dir "/home/user/PRD_benchmark/Python"
```

## Evaluation Scripts

The functionality of each script in the `/Evaluation` directory is as follows:

- **data_loader.py**: Extracts the six sections from the PRD and constructs different prompts based on the specified `setting`.  

- **generator.py**: Generates architecture diagrams in PlantUML format using the selected `generate_model`.  

- **uml_parser.py**: Parses the generated PlantUML diagrams and represents nodes in a hierarchical format (e.g., `layerA::layerB::node`) to facilitate structured evaluation.  

- **llm_judge.py**: Uses the `judge_model` to perform semantic similarity evaluation for generated nodes and produces intermediate alignment results in `judge_alignment.json`.  

- **arch_scorer.py**: Evaluates the generated architecture diagrams across four dimensions using prompts defined in `prompt.md`, and outputs intermediate scoring results in `arch_score.json`.  

- **metrics_calculator.py**: Conducts structural evaluation of the architecture diagrams, including Node F1 score, Edge F1 score, Layer Accuracy, and Graph Edit Distance (GED).

# Prompt template used in the experiment ✏️

## Extract PRD from the requirement document
```markdown
You are a professional software engineering requirements analyst. Please extract the following content based on the provided requirements document:

# Introduction
Please read the provided requirements document, focusing on the "Software Requirements Overview" and "Product Description" sections. Write a cohesive Introduction. 
**Requirements:**
* Summarize the overall scope of the project, explaining what kind of application it is.
* Specify the target users and the core pain points it aims to resolve.
* **Format:** Output as a fluent, continuous paragraph. Do not use lists.

# Goals
Please extract the project's Goals based on the "Product Features" section of the requirements document. Conduct a multi-point analysis of the features and list the specific objectives the system aims to achieve. 
**Format:** Use unordered lists (bullet points). Each goal should be concise and to the point.

# Features and Functionalities
Please carefully review the use cases section of the requirements document. Extract the system's Functional Features and rewrite each feature point strictly following this narrative structure: 
*"When [timing/trigger condition], [role/component] performs [action]."*
**Requirements:**
1. Cover various scenarios and edge cases as comprehensively as possible.
2. Categorize them logically by module wherever possible.

# Technical Constraints
Please search the requirements document and summarize the Technical Constraints of this project. Strictly adhere to a "fact-based" principle: only extract hard technical requirements explicitly mentioned in the document. Speculation is strictly prohibited. List them under the following categories (please add to the list if other constraints are found):
1. **Mobile Platform:** Supported operating systems.
2. **Backend Framework:** Specific development frameworks utilized.
3. **Database:** Storage and caching technologies employed.
4. **Programming Language:** The programming languages used to implement the project.

# Non-Functional Requirements
Please extract the system's Non-Functional Requirements based on the corresponding section in the requirements document. Categorize and organize the extracted content, including but not limited to the following aspects. Focus on macro-level quality goals and service-level agreements (SLAs); do not include specific technical tools or code-level constraints. Briefly explain the specific requirements for each item:
* **Processing Efficiency/Performance:** Requirements regarding response times and throughput.
* **Security:** Requirements regarding access control and data protection.
* **Availability:** Requirements regarding atomic operations and fault recovery/uptime.
* **Flexibility & Scalability:** Requirements regarding system expansion and maintainability.
* **Portability:** Requirements regarding cross-platform execution and deployment.

# System Architecture Description
Please read the document and factually extract the architecture description. Please map the information according to the following three dimensions:
1. **Application Layer**: The high-level layer. Focuses on specific business scenarios and native details, operating independently of hardware.
2. **Support Layer**: The middle layer. Acts as a "virtual machine" providing a cohesive set of common services (e.g., logging, caching) and serves as a bridge between layers.
3. **Infrastructure Layer**: The low-level layer. Built upon underlying computing, communication, and distribution mechanisms, completely independent of specific applications.
Please generate a natural language description of the system architecture. Do not extract specific components or detailed business logic; focus primarily on describing the overarching functions fulfilled by each layer and the interaction relationships between them.
```

## Convert to PlantUML format
```markdown
# Role
You are a senior system architect, highly skilled at converting complex system design diagrams into clear, standard PlantUML code.

# Goal
Please analyze the uploaded image of a system architecture and convert it into a standardized PlantUML architecture diagram.

# Design Framework (Formatting Specifications)
Please process and map the visual information according to the following rules:
1. **Unified Structure**: Adopt a top-down structure. Categorize components into the following four layers (adapt as necessary based on the provided image): 
   * Frontend/Client Layer
   * Network/Gateway Layer
   * Service/Backend Layer
   * Storage/Database Layer
2. **Styling & Beautification**: Assign distinct colors to nodes across different layers to visually differentiate them.
3. **Detail Handling**: Retain all Chinese functional descriptions from the original image. If specific technology stacks are mentioned (e.g., Django, React, MongoDB), indicate them within parentheses or represent them as independent nodes. Use arrows (`-->`) to represent data flow or invocation relationships.
4. **Consistency Requirements**: Apply logical naming conventions for all elements. Strictly avoid meaningless IDs (e.g., `node1`, `node2`). Use English abbreviations or functional Pinyin as IDs (e.g., `UserSvc[用户服务]`).

# Output Format
Output *only* the PlantUML code block. Do not include any surrounding explanatory text or pleasantries.
```

## Node Alignment
```markdown
# Role
You are a senior software architect. Your task is to evaluate whether the nodes and their [hierarchy/boundary attributions] in an AI-generated architecture diagram accurately reflect the Ground Truth (GT) of the human-designed architecture.

# Goal
Compare two lists of nodes (formatted as `Boundary/PackageName::NodeName` or `Global::NodeName`): a Ground Truth list (`GT Nodes`) and an AI-generated list (`Predicted Nodes`). Based on the provided PRD (Product Requirements Document) context, identify matching nodes based on semantic/functional equivalence and strictly evaluate if the AI placed them in the correct system boundary or architectural layer.

# Evaluation Rules (Crucial)
1. **Exact Match (1:1):** Direct equivalence between nodes. Includes two scenarios:
   * *Semantic Equivalence:* Different names but refer to the same component (e.g., GT "User Service" vs. AI "Account Management").
   * *Generalization/Specialization (is-a):* One is an abstraction or specific implementation of the other (e.g., GT "MySQL" vs. AI "Main Database", or GT "Payment Interface" vs. AI "Alipay Service").
2. **Split/Merge Match (1:N or N:1):**
   * *1:N:* A single broad GT node is split into multiple specific microservices by the AI.
   * *N:1:* Multiple granular GT nodes are aggregated into a single node by the AI.
3. **Boundary/Hierarchy Check:**
   * For successfully matched nodes, compare their `Boundary/PackageName`.
   * Evaluate as `true` if the boundary names differ but share the same architectural semantics (e.g., GT: "Backend::Data Layer::MySQL" vs. AI: "Database::MySQL").
   * Evaluate as `false` if there is a severe cross-boundary error or context confusion (e.g., a service belonging to the "Order Context" in GT is placed in the "User Context" by the AI, or a backend component is placed inside a frontend package).
4. **Unmatched Nodes:** AI hallucinations (surplus nodes) or omissions (missing GT nodes) must be placed in their respective unmatched lists.

# Input Data
* **PRD Summary:** {prd_summary}
* **GT Nodes:** {gt_nodes_list}
* **Predicted Nodes:** {predicted_nodes_list}

# Output Format
Output strictly in JSON format. Do not include Markdown code block markers (```json) or any extraneous explanations. Use the exact structure below:
{
  "matched_pairs": [
    {
      "gt_nodes": ["Backend::Auth Service"],
      "predicted_nodes": ["Gateway::Auth Center"],
      "match_type": "1:1",
      "is_boundary_correct": false,
      "reasoning": "Functional match (both are for authentication), but boundary error. GT places it in the backend microservice layer, while AI incorrectly assigned it to the gateway layer."
    },
    {
      "gt_nodes": ["Data Layer::User DB"],
      "predicted_nodes": ["Database::MySQL_User", "Database::Redis_User"],
      "match_type": "1:N",
      "is_boundary_correct": true,
      "reasoning": "The GT node was subdivided, but the semantic meaning of the database boundary remains consistent. Boundary check passed."
    }
  ],
  "unmatched_gt_nodes": ["Global::Payment API"],
  "unmatched_predicted_nodes": ["Frontend::Vue Router"]
}
```

## Large Model Scoring
```markdown
You are an expert Software Architect and an impartial evaluator. Your task is to evaluate an AI-generated system architecture diagram based on a set of strict criteria. 

You will be provided with:
1. <PRD_OR_GROUND_TRUTH>: The original Product Requirements Document or the Ground Truth architecture expectations. (If this is empty, evaluate blindly based solely on engineering common sense).
2. <PREDICTED_DIAGRAM>: The code (e.g., PlantUML, Mermaid) representing the AI-generated architecture diagram.

<EVALUATION_RUBRIC>
You must evaluate the diagram across four orthogonal dimensions. STRICTLY adhere to the Exemption Rules (No Double Jeopardy) to avoid penalizing the same mistake twice across different dimensions.

Dimension 1: Completeness (1-5 points) — "Is anything missing?"
* Core Definition: Evaluate strictly against the PRD. Check if all required components, storage systems, third-party dependencies, and core workflows are present.
* Exemption Rules: Do NOT penalize for extra/hallucinated components here. Do NOT penalize if connection directions are wrong, as long as the node exists.
* 5: 100% of business modules and technical components present.
* 4: Core skeleton covered, only marginal/non-core components missing.
* 3: Missing some important components, but main workflow is not broken.
* 2: Severe omissions (e.g., missing requested payment gateway or core DB).
* 1: Extreme lack of content, almost an empty shell.

Dimension 2: Accuracy (1-5 points) — "Is anything wrong or fabricated?"
* Core Definition: Evaluate strictly against the PRD. Are the drawn elements completely faithful to the document? Are there fabricated elements (hallucinations)? Are connections logical based on the PRD?
* Exemption Rules: Do NOT penalize for omitted components (already penalized in Dim 1). If a component improves the system but is NOT in the PRD (e.g., adding Redis for caching when not requested), it is a hallucination and MUST be penalized here.
* 5: 100% faithful, zero hallucinations, perfect connection directions.
* 4: Minor extra nodes (mild hallucination) or insignificant reversed connections.
* 3: Obvious hallucinated components, or clear logical errors in core workflows.
* 2: A large number of unmentioned components, or blindly connecting unrelated systems.
* 1: Components and relationships completely deviate from the PRD.

Dimension 3: Architectural Rationality (1-5 points) — "Can this system actually run?"
* Core Definition: Ignore the PRD completely. Rely solely on software engineering common sense. Review the topology for "Anti-patterns" (e.g., infinite loops, isolated islands, unauthorized cross-layer calls).
* Exemption Rules: Do NOT penalize here if the system looks broken simply because it "missed drawing the database" (penalized in Dim 1). Only penalize inherent logical flaws in the DRAWN graph.
* 5: Rigorous topology, clear layering, high cohesion, low coupling. No anti-patterns.
* 4: Generally reasonable, but individual nodes might be slightly bloated.
* 3: Barely usable. Minor architectural flaws (e.g., frontend bypasses gateway).
* 2: Clear anti-patterns: Isolated nodes (no connections) or circular dependencies.
* 1: Disastrous design violating basic engineering common sense (e.g., frontend directly writes to DB).

Dimension 4: Structural Readability (1-5 points) — "Is the code well-organized?"
* Core Definition: Based purely on the code syntax, evaluate if it makes good use of features (e.g., Package, Group, Boundaries) to organize hierarchy.
* Exemption Rules: Do NOT evaluate functional correctness here; strictly assess organizational form.
* 5: Excellent structure. Proficient use of boundaries/packages for clear modularity.
* 4: Generally clear, but grouping is not detailed enough.
* 3: Lacks hierarchy. Flat accumulation of code.
* 2: Chaotic code organization, no logical grouping.
* 1: Syntax contains redundancies, errors, or is completely unreadable.
</EVALUATION_RUBRIC>

<OUTPUT_FORMAT>
You must output your evaluation in standard JSON format ONLY. Do not include markdown code blocks (like ```json) in your final output, just the raw JSON object. Use the following schema:

{
  "chain_of_thought": "Briefly analyze the diagram step-by-step against the 4 dimensions before scoring. Note any exemptions applied.",
  "scores": {
    "completeness": {
      "score": <int 1-5>,
      "reasoning": "<1-2 sentences justifying the score>"
    },
    "accuracy": {
      "score": <int 1-5>,
      "reasoning": "<1-2 sentences justifying the score>"
    },
    "rationality": {
      "score": <int 1-5>,
      "reasoning": "<1-2 sentences justifying the score>"
    },
    "readability": {
      "score": <int 1-5>,
      "reasoning": "<1-2 sentences justifying the score>"
    }
  }
}
</OUTPUT_FORMAT>

</PRD_OR_GROUND_TRUTH>

</INPUTS>
