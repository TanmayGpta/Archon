# 系统介绍
持久化对象不一致检测软件（POCD）是一款旨在解决软件开发过程中模型与数据库结构同步失效问题的自动化检测与修复工具 。该系统主要面向具有较强技术背景的研发、测试及 IT 运维人员，旨在解决因业务迭代导致的代码类图与数据库模式不一致所带来的系统性能下降、需求追踪困难及项目验收风险等核心痛点 。通过自动化解析数据库脚本与 UML 类图，POCD 能够精准识别字段、类型及类间关系的冲突，并提供可视化的修复建议，从而减轻开发人员的手动维护负担，提升系统的数据一致性与稳定性 。

# 核心目标
+ **自动化解析与呈现**：实现对数据库设计文件（MySQL）和类图存储文件（StarUML）中关键信息的深度解析与可视化展示 。
+ **全方位冲突检测**：精准检测类与表、属性与列、字段名称、数据类型以及类间多重性和关系类型的不一致性 
+ **闭环修复机制**：根据检测结果生成修复建议，并在用户授权后自动执行数据库或类图的更新操作 。
+ **灵活的规则配置**：允许用户自定义检测项参数、配置检测算法以及设置特定的检测例外规则 。
+ **历史追溯与管理**：提供文件上传下载功能，并持久化存储历史检测记录与修改日志以便追溯 。
+ **降低使用门槛**：通过提供新手教学引导、帮助手册及检测案例，提升非熟悉用户的易用性体验 。


# 功能特性
**账户与权限模块**

+ 当未注册用户需要加入系统时，该用户进行输入个人信息并提交注册的操作 。
+ 当已注册用户需要使用系统功能时，该用户进行输入账号密码并执行登录动作 。

**文件与资源管理**

+ 当已登录用户需要分析数据时，该用户进行上传类图（.mdj）或数据库（.sql）文件的动作 。
+ 当已登录用户需要整理文件时，该用户进行修改文件名或执行文件删除的动作 。
+ 当已登录用户需要导出资料时，该用户进行下载类图、数据库文件或检测报告的动作 。
+ 当用户需要学习系统使用时，该用户进行查询帮助手册或下载检测案例的动作 。

**解析与提取模块**

+ 当系统接收到类图文件时，类图解析器进行提取类、属性及关系信息的动作 。
+ 当系统接收到数据库文件时，数据库解析器通过 JDBC 进行提取表名、字段、主键、外键及触发器信息的动作 。
+ 当系统扫描数据库结构时，业务逻辑层进行识别外键和触发器所蕴含的关系类型动作 。

**不一致检测模块**

+ 当用户启动检测任务时，系统通过二分匹配算法进行实体类与实体表的一一对应匹配动作 。
+ 当实体匹配完成后，系统进行类名与表名、属性名与列名的字段不一致检测动作 。
+ 当属性建立对应关系后，系统进行属性数据类型与数据库列类型兼容性的比对动作 。
+ 当执行深度检测时，系统进行多重性上界/下界、聚合/组合/继承关系类型的冲突检测动作 。

**修复与追溯模块**

+ 当检测到不一致项后，系统进行修复建议的生成并展示给用户进行勾选动作 。
+ 当用户确认修复指令后，系统按照正确的拓扑顺序进行类图或数据库的自动修复动作 。
+ 当用户需要复盘变更时，系统进行展示历史不一致检测信息与修改记录的动作 。

# 技术限制
+ **移动端平台**：支持 Android 和 iOS（针对 Gemini Live 模式相关辅助功能）。
+ **后端框架**：使用 Java 技术栈，提及 Jackson 用于 Json 转换，基于 JDBC 的数据库连接器 。
+ **数据库**：存储技术使用 **MySQL**；支持解析 MySQL 脚本并内置临时数据库进行分析 。
+ **编程语言**：实现项目主要使用 **Java** 。

# 非功能性需求
+ **处理时效**：系统应支持高性能分析，需在 30 分钟内完成包含数千个实体的大型数据库检测 ；同时支持异步处理，允许用户在检测时进行其他操作 。
+ **安全性**：敏感数据传输必须采用 SSL 加密 ；实施基于角色的访问控制（RBAC）；系统需记录操作日志并定期进行安全审计 。
+ **可用性**：系统应确保高可用，提供明确的操作反馈（如成功、错误、等待状态）；事务管理应确保操作的原子性 。
+ **灵活性**：采用前后端分离及分层模块化设计 ；提供开放的 API 接口以支持第三方集成 ；数据库设计需具备前瞻性以容纳未来数据结构的增加 。
+ **易用性**：主观交互需符合人体工程学，确保核心功能点击不超过三次即可触达 ；提供新手教学和示例文件，支持非登录状态下的核心功能体验 。


# 系统架构描述

### 1. 应用层 (Application Layer)

应用层直接承载了智能标注与知识挖掘两大核心业务场景 。它专注于特定领域的业务逻辑实现，如多学科标注预设的配置、复杂的项目流转管理（创建、分配、验收）以及基于科研需求的模型微调与反馈循环 。此层通过现代 Web 界面与用户交互，屏蔽了底层复杂的技术实现，确保科研人员能够聚焦于文献处理与知识发现 。
### 2. 支撑层 (Support Layer)
支撑层 通过微服务架构实现模块间的低耦合通信，为上层应用提供高度内聚的通用服务集合 。该层负责桥接业务逻辑与底层资源，具体职责包括：
* **自动化转换服务**：将非结构化的 PDF 文档转化为可处理的文本格式 。
* **智能调度服务**：对接大语言模型（如 GPT 系列）进行信息自动化提取与实体识别 。
* **安全与质量管控**：实现基于角色的访问控制（RBAC）、数据加密审计以及标注质量的校验 。
* **社区协作机制**：管理模型、语料库及预设配置的共享分发 。

### 3. 基础层 (Infrastructure Layer)

基础层是整个系统的物理与逻辑基石，专注于底层的数据持久化、通信协议与运行环境。它通过 MySQL 维护关系型数据，利用 Neo4j 构建复杂的知识图谱联系，并由 Redis 提供高并发下的响应支持 。同时，基础层利用 Minio 实现海量文献的非结构化存储，并在 Linux 环境下通过 HTTPS 协议保障数据传输的物理安全 。该层与具体业务无关，旨在为上层提供稳定、可扩展的计算与存储能力
